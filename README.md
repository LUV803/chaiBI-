# ChatBI 零售数据分析助手

**一个基于 LangGraph + MCP 的对话式 BI 助手**：用户用自然语言提问，系统一站式完成
意图分流 → 取数（Text2SQL）→ 统计分析 → 机器学习建模 → 图表绘制。
后端查询 PostgreSQL 业务库（零售商品月度销量 / 用户画像 / 用户活跃），
模型生成的 Python 代码在带审计钩子的沙箱子进程里执行，数据库访问走三层只读防护。

## 项目亮点

> **如果只能让面试官记住一件事**：这不只是个"跑通了的 demo" ——
> 我在这类系统里定位了一类**有数据支撑的错误答案**，并且**量化了自己没修好的那部分**。

- **定位了一类"有数据支撑的错误答案"**：模型会在问题所需维度不存在时，
  换一个能自圆其说的口径作答，给出一个**格式正常、有真实数据支撑、语气确信**的错误数字 ——
  比抛异常危险得多，因为用户没有理由怀疑它。加提示词约束后**仍有约 1/3 复发率**
  （7 次复现 2 次），且复发形态从"静默替换"变成"先自曝口径"——
  说明约束改变的是失败的**可见性**，不是**发生率**，根因在数据层不在提示词层。
  → [详见](#已知失效模式与处理)
- **Python 代码执行沙箱**：模型生成的代码在隔离子进程中运行，用 `sys.addaudithook`
  拦截网络、进程、注册表与越界文件访问 —— 纯 Python 层实现，跨平台，不需要容器或 root。
  → [详见](#1-python-代码执行沙箱)
- **SQL 只读的三层防护**：文本层 + 连接层 + 资源层。设计前提是
  「**提示词不是安全边界**」—— 单靠 system prompt 里写一句"不要执行 DML"拦不住任何东西。
  → [详见](#2-sql-只读的三层防护)
- **提示注入测试**：4 类注入（直接指令 / 数据字段内嵌 / 角色扮演 / base64 编码）
  均未被攻破，**硬断言是跑前跑后的数据行数快照**，不是回复措辞。
- **两层测试**：30 个用例的**回归测试**（改代码后验证有没有打坏别的东西）
  + 23 个用例的**行为评测集**（改提示词/换模型后看答对率是升是降，两次全量均 22/23）。

## 架构

### 拓扑

```
用户
 │
 ▼
chat_api  (FastAPI, :9008)
 │  lifespan 里建图一次并复用（不是每请求重建 —— 重建会重连 4 个 MCP 并重新拉取工具列表）
 ▼
LangGraph 工作流
 │
 ├─ call_identify_intention ──► ywfl_tool (:9005)   意图分流
 │       │
 │       ├─「纯python编码」     ──► call_python_coder ──► run_python_script_tool (:9002) ──► END
 │       │
 │       ├─「业务数据查询分析」 ──► list_tables_tool (:9004)
 │       │                              └─► data_analysis_agent  (ReAct 子图)
 │       │                                        ├── db_sql_tool                (:9004)
 │       │                                        ├── run_python_script_tool     (:9002)
 │       │                                        └── 机器学习工具 ×3             (:9003)
 │       │                                                  └─► END
 │       │
 │       └─ 其它（自由对话）  ──► END
 ▼
回复 + 图片路径（/images 静态目录直接可访问）
```

> 分流的两个标签来自提示词里写死的业务分类，模型必须原样返回这两个词之一；
> 代码侧做了归一化匹配（去空格/标点/书名号），避免模型多写一个句号就整轮流终结。

### 四个 MCP Server

| 端口 | 服务 | 传输方式 | 提供的工具 |
|---|---|---|---|
| 9002 | `python_chart_mcp` | streamable-http | `run_python_script_tool`、`translate_to_python_plot_script` |
| 9003 | `machine_learning_mcp` | streamable-http | `analysis_product_reviews_tool`、`reviews_stars_correlation_test_tool`、`sales_predict_tool` |
| 9004 | `statistic_db_mcp_tools` | **SSE** | `list_tables_tool`、`db_sql_tool` |
| 9005 | `ywfl_mcp` | streamable-http | `ywfl_tool` |

### 为什么拆成 4 个 MCP Server，而不是一个大服务

**一句话**：这 4 个服务的能力、故障特征、权限等级都不一样 —— 拆开是为了让它们
**各自失败、各自重启、各自持有最小凭据**，不是为了架构图好看。

| 维度 | 拆开的收益 | 本项目里的具体体现 |
|---|---|---|
| **权限边界** | 数据库连接串只活在一个进程里 | 主干链路上 `user` / `password` / `db_host` 只在 `statistic_db_mcp_tools.py` 出现；9002 / 9003 / 9005 完全不碰库 |
| **故障隔离** | 沙箱跑飞不拖垮查库 | 执行超时杀的是 9002 拉起的**子进程**；即便 9002 整个挂掉，9004 的 SQL 链路照常 |
| **独立迭代** | 改一处只重启一个 | 调沙箱白名单只重启动 9002；改分流提示词只重启动 9005 |
| **能力复用** | 4 个都是标准 MCP server | 任何 MCP 客户端都能直接接，不依赖这个 LangGraph host |

**代价（这部分必须讲，只讲优点会显得没想过）：**

- **启动更麻烦**：4 个进程手工拉起，还得记住"改了代码要重启**对应的那个**"
- **链路更长**：每次工具调用多一跳进程间通信，调试时要同时盯多个终端
- **没有统一日志**：4 份 stdout 各打各的，一次跨服务的链路问题要拼着看
- **装配有成本**：`chat_api.py` 的 `lifespan` 里建图一次并复用，正是为了避免
  每请求重连 4 个 MCP、重新拉一遍工具列表

**对比：为什么不干脆用 `create_react_agent` + 一个扁平工具列表？**

8 个工具（读表结构 / 写 SQL / 跑 Python / 情感分析 / 相关性检验 / 销量预测 / 绘图 / 分流）
全塞进一个 ReAct loop 的话，模型**每一轮都要在这 8 个里重新选一次**，
而且"这一轮该走哪条业务线"这个决策没有任何确定性保证。

本项目的做法是**分两层**：外层状态机负责一次性的、确定性的业务分流（走哪条支线），
内层 ReAct 子图只在「业务数据查询分析」这条支线内部做探索式多步取数。
分流结果决定走哪条边 —— 模型不需要每轮重新决策流程本身。
详见 [编排与分流](#3-编排与分流)。

## 关键技术决策

### 1. Python 代码执行沙箱

**问题**：`run_python_script_tool` 要执行**模型生成的**代码。最初的实现是直接在 MCP
进程里 `exec()` —— 等于把任意代码执行权交给了一个可能被提示词注入的模型。

**方案**：子进程隔离 + 审计钩子。

```
python_chart_mcp (父进程)
  └─ subprocess.run([sys.executable, py_sandbox_runner.py, 脚本, 工作目录, 配置],
                    timeout=20s, env=最小环境变量)
       └─ 子进程：sys.addaudithook(...) → eval/exec 用户脚本（受限 builtins）
```

| 防线 | 拦截手段 |
|---|---|
| 进程 | 独立子进程，超时杀掉，不污染宿主进程 |
| 系统调用 | `sys.addaudithook` 拦 `os.system`/`subprocess.Popen`/`socket.*`/`ctypes.call_function`/注册表写入 |
| 文件 | 白名单写根目录（工作目录 + 绘图输出目录），黑名单禁读（项目根目录、用户主目录） |
| 语言层 | 受限 `__builtins__`：import 白名单（matplotlib/numpy/pandas/…），移除 `eval`/`exec`/`compile`/`open`/`__import__` |
| 资源 | 输出上限 200KB、返回变量上限 20 个、执行超时 20s |

**威胁模型先定清楚**：要防的是「**模型写错代码**」—— 它可能误删文件、误发网络请求、
写出死循环，但它**不是在针对性地攻击我**。这个前提决定了防护等级：
目标是**提高越权成本 + 限制爆炸半径**，不是构造一个能扛住主动逃逸的沙箱。

**为什么不用那三个更"重"的方案：**

| 方案 | 拒绝原因 |
|---|---|
| **seccomp** | Linux 专有，本项目跑在 Windows 上，直接用不了 |
| **Docker / 容器** | 要装 Docker、要拉镜像，单次执行多几百毫秒启动开销；对一个 demo 级项目是过度设计 |
| **RestrictedPython** | 它在**语法层**做 AST 改写，而 matplotlib / numpy / pandas 的正常调用会大面积触发它的限制 —— 画个图就废了 |
| **`sys.addaudithook`** ✅ | **纯 Python 标准库、跨平台、零额外依赖**，且能覆盖到 `import` / `open` / `socket` / `subprocess` / `ctypes` 这一类真正敏感的事件 |

**它的局限（这点必须自己说出来）：**

审计钩子看不见**已经加载的库内部发起的调用**。比如 `numpy` 内部如果通过 C 扩展请求网络，
Python 层的 hook 未必拦得住。所以本项目**没有**去把 `open` 从 builtins 里摘掉就完事 ——
那样只会让正常绘图挂掉，却挡不住真正绕过的路径。

真正的文件防线落在**hook 自己的路径判定**上：不区分调用来源，只看"这个路径在不在白名单里"。
这也是它能在受限 builtins 之外**再兜一层**的原因：即使某个库内部偷偷打开了项目根目录的文件，
路径判定照样拦下。**纵深防御的位置比单层的完美更实在。**

**实测拦截效果**（`regression_test.py` 里固化成了用例）：
`import os` 被拦 / 读项目 `.env` 被拦 / 写工作目录外被拦且无残留文件 /
死循环被超时杀掉 / 输出洪水被截断 —— 而正常绘图与中文渲染不受影响。

### 2. SQL 只读的三层防护

**设计前提：提示词不是安全边界。** 原实现直接执行模型给的 SQL，
唯一的"防护"是 system prompt 里的「不要执行任何 DML 语句」。
而连接用的还是 postgres 超级用户账号 —— 这意味着提示词一被绕过，就是全库可写。

| 层 | 位置 | 做什么 |
|---|---|---|
| 文本层 | `check_read_only()` | 只允许 `SELECT/WITH/TABLE/VALUES/SHOW/EXPLAIN` 开头；先剥离注释、字符串字面量、双引号标识符，再扫描写类关键字（防止 CTE 里藏 `DELETE`）；拒绝多语句拼接 |
| 连接层 | `connect_args.options` | `default_transaction_read_only=on` —— **由 PostgreSQL 自己拒绝**，即使文本层被绕过也写不进去 |
| 资源层 | 同上 + 返回裁剪 | `statement_timeout=15s`、返回行数上限 200 |

**为什么必须有连接层**：文本层的白名单/黑名单是"我能想到的攻击方式"，
而只读事务是数据库的语义保证。实测直接绕过工具、用连接执行 `INSERT`，
PostgreSQL 返回 `ReadOnlySqlTransaction`，数据完好。

**这三层不是生产级方案，差的地方我很清楚：**

| 缺什么 | 为什么是问题 |
|---|---|
| **专用低权限账号** | 现在连的还是 postgres **超级用户**。只读事务是"当前这次会话不写"，不是"这个账号不能写" —— 账号本身仍有权。生产上必须换成只授 `SELECT` 的角色，让**权限**而不是**语句**来兜底 |
| **审计日志** | 谁在什么时候跑了什么 SQL、返回多少行 —— 一条都没记。出事之后无法回溯 |
| **行级权限（RLS）** | 所有查询者看到的是同一份数据。多租户/多部门场景下，"只读"也意味着**能读全部** |
| **并发控制** | `chat_api.py` 是单进程（没有 `--workers`），也没有限流。真正的瓶颈不是"能不能写"，而是**同时来 10 个查询会不会把库拖死** |

**"只读"拦不住的那一类 —— 这才是我最想说的：**

只读**只保证不改变数据，不保证不消耗资源**。一条 `SELECT` 照样可以：

- 全表扫描 + 大排序，把 shared_buffers 冲干净
- `generate_series(1, 100000000)` 这种纯计算查询，不碰任何表也能吃满 CPU
- 自己和自己做笛卡尔积，把临时表撑爆

我做的应对只是**资源层的两个硬上限**（`statement_timeout=15s`、返回最多 200 行）——
这两个数是**拍的，不是压测出来的**。真实并发下它们该定多少，我没数据。
**这是一处我知道自己没验证、也不敢说它够用的地方。**

### 3. 编排与分流

**分层的理由：两类决策的性质完全不同。**

| | 外层分流 | 内层 ReAct 子图 |
|---|---|---|
| 决策频率 | **每轮对话一次** | 每一步都可能一次，次数不定 |
| 决策内容 | 走哪条业务支线 | 这条支线内部"下一步查什么" |
| 确定性 | **可以做到确定**（就两个标签） | 天然探索式，无法预定步数 |
| 出错的代价 | **整轮走错流程**，后面全白做 | 多查一次或少查一次，能自己纠回来 |

把这两类决策**放进同一个 loop**，等于让模型在每一轮都重新决定"我是不是还该走这条路" ——
它没有任何机制保证第 5 步还认第 1 步的判断。而分流放在外面，**结果定下来就决定了走哪条边，
模型没有机会反悔**。这就是"外层状态机 + 内层 ReAct"的分工。

**为什么分流要做成一个独立 MCP 工具，而不是本地 if-else？**

因为**分流是语义判断，不是关键词匹配**。「帮我画个折线图」和「商品销量趋势怎么样」
表面都不含"编码"二字，但一个该走绘图支线、一个该走查库支线 —— 关键词表写不出这个区分，
**只有模型能判断**。既然必须调模型，那就把它做成和其他能力同构的 MCP 工具：
复用同一套装配方式、同一套超时与错误处理，未来换模型/换提示词也只动 9005 一个服务。

**扩展性 —— 这是这套结构真正的好处：**

分流节点处在流程的**最前端**，它输出的标签唯一决定下游走哪条边。
所以再要加一条业务线（比如"报表导出"）时，**只需要新增一条边和它下游的节点**，
已经开发好的节点和支线**一行都不用改**。新增的是分支，不是修改。

**兜底：为什么不能让它静默结束。**

原实现里标签匹配是这样的：

```python
if text == "纯python编码":      # ← 精确相等
```

模型只要多输出一个句号、一对书名号、或者前后多一个空格，就不匹配任何分支，
**整图直接走到 END，用户什么都收不到** —— 一个纯粹的形状问题变成了完全的空响应。

修法是两步：**匹配侧归一化**（去空格/标点/书名号 + 子串匹配），
加上 **`should_continue_ywfl()` 兜底：认不出标签就当自由对话，正常回话**。

这里的原则比修法本身重要：**"认不出来"的默认行为，必须是代价最小的那条路。**
分流不确定时，最坏的选项是"什么都不返回"（用户看到空白，无从判断是坏了还是没说完）；
次坏是"猜一条支线"（可能跑一堆无关的工具）；
"当作自由对话正常回答"最差也只是没帮上忙，但**用户看得见**、也知道该换个说法重问。
**失败的可见性，比失败本身更值得设计。**

## 已知失效模式与处理

<!-- 这一节是这份 README 最有价值的部分。多数简历项目只写"实现了什么"，
     不写"它在哪儿会错"。能讲清楚失效模式，说明你真的跑过、debug 过。 -->

| # | 失效模式 | 表现 | 为什么危险 | 处理 |
|---|---|---|---|---|
| 1 | **维度不存在时悄悄降级** | 问「运动类商品有多少」，但 `product` 表没有品类字段。模型不拒绝，而是把问题换成「商品名含'运动'二字」，答"共有 1 款（运动饮料）" | 这个数字**有真实数据支撑**、格式正常、语气自信 —— 用户几乎不可能发现它答的是另一个问题。比抛异常危险得多 | 提示词强制「先核对维度是否存在」，不存在就明说并列出可用字段；明确禁止用 `LIKE`/`position` 替代不存在的维度 |
| 2 | **把 LIMIT 行数当成总数** | 模型用 `SELECT ... LIMIT 30` 取回 30 行，就对用户说"该表共 30 条"（真实 301 行 / 196 个不同商品） | 同上：一个看起来权威的错误数字。根因是提示词里"限制最多 30 个结果"被模型当成了数据事实 | 要求统计总数必须**单独跑聚合查询**；看到"结果已截断"提示时不得下"总共多少"的结论 |
| 3 | **子图内部不可观测** | `astream(stream_mode="values")` 看不到 `data_analysis_agent` 子图内部的 `db_sql_tool` 调用，日志里从"取表结构"直接跳到最终答案 | 排查"模型到底跑了什么 SQL"时完全抓瞎 —— 失效模式 1 和 2 之所以难发现，一半原因在这 | `astream(..., subgraphs=True)` 把子图步骤也流出来；回归测试据此断言"它确实查过" |
| 4 | **LIKE 查询整体不可用**（已修） | `exec_driver_sql` 遇到 `%` 会当成 psycopg2 的参数占位符，`LIKE '%关键字%'` 直接报 `immutabledict is not a sequence` | 这是 Text2SQL 最常见的写法。更麻烦的是模型会**自愈**：改用 `position()` 绕过 —— 它能继续答题，但你不知道它换了条件 | 改用原生 DBAPI 游标，绕开 SQLAlchemy 参数处理层 |
| 5 | **`NOT IN` + NULL 导致静默返回 0** | `product` 表有 1 行 `product_name IS NULL`；`NOT IN (子查询)` 展开后含 `x <> NULL`，三值逻辑下**整个 WHERE 恒假**，返回 0 行（正确 679） | 同 1、2：不报错、格式正常、看起来像个正当答案 | 用 `NOT EXISTS` 或 `LEFT JOIN ... IS NULL`；标定答案时**必须和独立数字交叉验证**（`196 + 679 = 875`）|
| 6 | **保留字陷阱：SQL 层真实，但链路不可达**（已验证不触发） | SQL 层 `SELECT count(*) FROM user` 确实返回 **1**（正确 13），因为 PG 把它解析成当前用户伪列 | ——**实测模型自己给 `user` 加了双引号，答对 13**。`"user"` 在训练数据里太常见，先验足够强 | **不修**。这是个**证伪案例**：查 SQL 层确认问题真实存在 → 预测模型会踩 → 写用例去测 → **没踩**。用例留在 `regression_test.py` 里，作为"这个坑已被验证不触发"的存档 |

> 💡 **第 6 行值得单独说**：它记录了"**缺陷存在 ≠ 缺陷可达**"。
> 在代码里找到一个真问题，不代表它在实际链路里会发生 —— 中间隔着模型行为这一层。
> 这个结论只能靠**写用例去跑**得到，靠推理会得出相反答案（我第一版就是错的）。

**1、2、5 是同一个病的三个症状。**

| # | 它把什么当成了事实 |
|---|---|
| 1 维度不存在 | 把「名字里含'运动'」**当成了**「运动类目」 —— 换了个能算的口径继续算 |
| 2 LIMIT 截断 | 把「返回了 30 行」**当成了**「总共有 30 条」 —— 拿看得见的部分当全体 |
| 5 `NOT IN` + NULL | 把「查出来是 0」**当成了**「确实是 0」 —— 空结果直接当结论，没怀疑是查询本身错了 |

三者的共同点不是"算错了"，而是**模型从不区分"我知道"和"我猜的"**：
遇到答不了的问题时，它会**换一个能答的问题去答**，然后用回答真问题的语气说出来。
结果是格式正常、有真实数据支撑、语气确信 —— **有数据支撑地答错**。

**为什么修完 #1 没防住 #2？**

因为前两次都是**逐个修症状**：#1 加了一条"维度不存在要明说"，
#2 加了一条"统计总数要单独聚合"—— 都是**针对某个具体失误**的补丁。
换一个新场景（#5），规则覆盖不到，就再犯一次。

真正该立的是**一条通用规则**：**结论必须能自证。** 具体落地成三条要求：

1. **复述理解** —— 说清"我把这个问题理解成了什么"
2. **交代字段** —— 用了哪些列、按什么口径
3. **交代筛选条件** —— 带了哪些 WHERE、结果是全量还是截断

满足这三条，上述三种错误**都会在输出里露出马脚**。因为它们的共同前提是
"用户看不出我问的是另一个问题" —— 一旦模型必须把理解写出来，这个前提就不成立了。

**另一个原则：分清哪些能靠提示词修，哪些只能靠数据层修。**

#1 加完约束后**仍有约 1/3 复发率**（7 次复现 2 次），而且复发形态从
"静默替换口径"变成了"先自曝口径再答" —— 这说明我改变的是**失败的可见性**，
**不是失败的发生率**。根因很清楚：`product` 表**根本没有 `category` 字段**，
模型拿不到那个维度，就只能在"拒绝回答"和"换个口径"之间选，而它倾向于选后者。

**数据缺失的问题，提示词只能让它暴露，不能让它消失。** 所以正确的动作是
`add_category.py` 补上那一列 —— 那是数据层的事，不是提示词层的事。

**最后一个原则，也是最反直觉的一条：光靠读代码判断不出来。**

失效模式 6 是个**证伪案例**：我读 SQL 层确认 `FROM user` 会返回错误结果（确实返回 1，正确 13），
据此预测模型一定会踩这个坑，专门写了用例去测 —— **结果模型自己给 `user` 加了双引号，答对了**。

**缺陷存在 ≠ 缺陷可达。** 中间隔着"模型实际会怎么写"这一层，
而这一层**只能靠跑用例测出来，靠推理只会得到相反答案**（我第一版就是错的）。
所以本项目的每个失效模式后面都跟着一个用例，**没跑过的判断我不写进来。**

## 测试

`chatbi_graph/regression_test.py` —— 30 个用例，两层设计：

```bash
python regression_test.py              # 离线层：27 个用例，不调模型、不花钱、几秒出结果
python regression_test.py --with-llm   # 追加 3 个行为用例（会消耗 API 额度）
```

- **离线层**（确定性）：4 个 MCP 服务可达性、8 个必需工具齐全、SQL 只读拦截、
  `LIKE`/`::`/中文列名可用、0 行结果表述、沙箱三类越权拦截 + 正常绘图不受影响、
  图拓扑、分流归一化。
- **大模型层**（行为）：断言的是**行为**而非字符串 —— 维度不存在时必须拒绝、
  总数统计必须去重、正常查询要复述筛选条件。

退出码 0/1，可直接接入 CI。

**为什么行为层单独拆出来、且默认不跑：**

| | 离线层（27 条） | 大模型层（3 条） |
|---|---|---|
| 结果 | **确定性**，同样的输入永远同样的结论 | **概率性**，同一句问法可能时对时错 |
| 成本 | 免费、几秒 | 每次消耗 API 额度、几十秒 |
| 挂了意味着 | **改坏了东西** —— 必须修 | **这次没答好** —— 不一定是代码问题 |
| 该怎么用 | **回归测试**：必须全绿，红了就 blocking | **评测集**：看**通过率**，不是看红绿 |

这个区别决定了它们不该混在一起跑。离线层进 CI 是应该的 ——
它拦截的是"我改 A 结果打坏了 B"这类**纯回归**问题，跑一次几秒钟，性价比极高。

行为层默认不跑，是因为**它红了不等于有 bug**：模型有随机性，同一条用例今天过明天不过。
拿它当门禁，团队每天都得处理假报警，最后所有人都会习惯性忽略它 —— 那还不如不设。

**什么时候才把它加进 CI：只在你改了会改变行为的三样东西之后 ——
提示词、模型、工具 schema。** 这三种改动离线层一条都拦不住
（代码没变，断言当然全绿），而它们恰恰是最容易让答对率掉下去的地方。

**还有一个统计口径上的细节值得说**：我跑过两次全量 23 条，**两次都是 22/23**，
但**挂的不是同一条用例**。如果只看"22/23"这个数字，会得出"稳定"的结论；
看到具体是哪条挂了，才知道那 1 条其实是**随机波动**，不是稳定缺陷。
**通过率一样不代表表现一样 —— 只看总数会把噪声读成信号。**

### 关于 `tools_node.py`：为什么保留它

它记录的是**另一条实现路线** —— LangChain 官方 `SQLDatabaseToolkit` 的本地装配方式，
主干最终没走它。保留有两个原因：一是备查，二是它把这个选择讲清楚了。

**主干为什么没选本地 toolkit：**

- **凭据会进错进程**：toolkit 要在 LangGraph host（`chatbi_graph/`）里直接持有数据库连接串。
  而现在 `user` / `password` 只活在 9004 一个 MCP 进程里 —— 走 MCP 才能守住这条边界
- **实现和编排耦合**：数据库工具的实现细节会长在图定义旁边，
  想单独换掉/单独部署做不到

**顺带说一个更好的理由 —— 它自己的 docstring 里记着两个真实的坑：**

1. 原实现在**模块导入时**就执行了 `SQLDatabase.from_uri(...)` ——
   结果"导入一个提示词模块"都需要数据库在线，本地没起 PG 就 import 失败
2. 裸写 `postgresql://` 在 SQLAlchemy 2.1 下默认走 psycopg**3**，
   而环境里装的是 psycopg**2**，直接 `ModuleNotFoundError`（这个是真踩过的）

坑 1 的教训被固化成了现在的设计：**`prompts.py` 是个纯数据模块，导入它没有任何副作用。**
把"导入即副作用"清掉之后，提示词可以脱离整个运行时单独被 import、单独被测试。

## 数据说明

演示用 PostgreSQL 库 `sales_chat`，4 张表：

| 表 | 行数 | 去重后 | 说明 |
|---|---|---|---|
| `user` | 13 | — | 用户基本信息（含 `self_description`、`occupation`）|
| `product` | 301 | **196** 个商品名 | 商品（`product_no` / `product_name` / `product_price`）|
| `sales` | 980 | **875** 个商品名 | 各商品 1~12 月销量（**中文列名**，查询需双引号）|
| `user_active` | 40 | — | 用户活跃记录（**中文列名**）|

> ⚠️ 已知数据问题，演示时请注意：
> - `product` 有 301 行但只有 **196 个不同商品名** —— 存在重复行，
>   「有多少种商品」必须用 `count(DISTINCT ...)`，否则会多算。
>   且**同名商品有不同价格**（`三七` 同为 7.0/7.5，`人参` 同为 9.0/9.5），
>   所以「XX 多少钱」这类问题本身有歧义。
> - `product` **没有品类字段**，所以「运动类/食品类商品有多少」这类问题
>   **设计上就无法回答**（这正是失效模式 1 的触发场景）。
>   跑 `add_category.py` 可以补上这一列。
> - ⚠️ **`user` 是 PostgreSQL 保留字，SQL 里必须写成 `"user"`** ——
>   裸写 `SELECT count(*) FROM user` **不报错**，而是返回 **1**（正确是 13）。
>   注意：**模型自己会加引号**，端到端实测答对（见失效模式 6）。
> - ⚠️ **`product` 有 1 行 `product_name IS NULL`** —— 用 `NOT IN` 查
>   "sales 里有多少商品不在 product 里"会**静默返回 0**（正确 679）。
>   必须用 `NOT EXISTS` 或 `LEFT JOIN ... IS NULL`。见失效模式 5。
> - 所有表和字段都**没有注释** —— `list_tables_tool` 支持读取注释，
>   补上注释对模型理解字段语义帮助很大。

## 待改进

**先说清楚这份清单的性质**：这些都是**我知道、但没修**的问题 ——
不是没想到，是权衡后没做，或者还不知道做到什么程度算够。
这两种"没修"很不一样，所以末尾按**欠债类型**把它们分了三档，**每档该怎么答写在最后**。

**1. 数据库账号还是超级用户**（安全）
三层防护挡的是"这次会话不写"，挡不住"这个账号本来就能写"。
换低权限账号是配置工作不是开发工作，但**它就是没做**。这是我知道的最大的一个缺口。

**2. 没有对话记忆**（体验）
`MemorySaver` 装配了但没启用，多轮上下文靠前端把 history 拼成文本再传一遍。
所以"那第二个月呢"这类追问，模型只能从拼接的文本里猜指代 —— 指错了也没有机制纠正。

**3. `analysis_product_reviews_tool` 注释说并行，实际是串行**（一致性）
里面逐条评论调模型，注释写的却是并行。功能正确、速度慢，**但注释在说谎** ——
比没有注释更糟，因为下一个读代码的人会信它。

**4. 意图分流对措辞敏感**（鲁棒性）
「商品一共有多少种」会被判成自由对话，加"查询"二字就正常。
同一个意思换个说法结果不同 —— 说明分流的边界不够稳，而我只测了有限几种问法。

**5. `IMAGE_DIR` 环境变量代码里从没被读取**（死配置）
写在 `.env` 里但没人读，属于历史残留。**看起来可配置，实际改了没用** ——
这类"假的可配置项"比没有配置更容易误导人。

**6. 没有并发压测**（性能）
`chat_api.py` 是单进程、没有 `--workers`，`.env` 里的资源上限（`statement_timeout=15s`、
返回 200 行）是**拍的，不是压出来的**。真实并发下该定多少，我没有数据。
**这是缺陷存在与缺陷可达之间那道鸿沟，我自己也还没跨过去。**

**7. 没有语义层**（可维护性）
所有表和字段都没有注释，`list_tables_tool` 明明支持读注释。
模型对字段语义的理解全靠字段名本身 —— 8 个工具的能力上限，
最终是被这一层卡住的，不是被模型卡住的。

---

**按"欠债类型"分三档，它们的答法完全不同：**

| 档 | 条目 | 该说什么 |
|---|---|---|
| **明确欠债** | 1、2、3 | 改法清楚、只是没做。答**"为什么现在不做"**（优先级，不是能力） |
| **明确的坏味道** | 4、5 | 改法也清楚，但它们不抛异常、只是让人别扭。答**"它现在怎么咬人"**（比如第 5 条：改了 `IMAGE_DIR` 没有任何效果） |
| **还不知道怎么判** | 6、7 | 不是不会改，是**不知道该做到什么程度算够**。答**"我打算怎么验证它够不够"** —— 这一档最诚实，也最难答 |

**最后这条值得单独说**：主动写出局限，比等人问出来强。
但**写出局限 ≠ 示弱** —— 区别在于你有没有同时说清"我知道该怎么收",
还是它只是被你撞见了。这份清单里前五条属于前者，后两条属于后者。**别把两类说成一样。**
